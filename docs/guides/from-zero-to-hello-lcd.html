P0

建立通信

先证明电脑能看见这块板。这一步不做，后面所有判断都建立在假设上。

判据实测含义
VID_303A命中Espressif 原生 USB，不是 CH340 / CP210x 桥接
PID_1001命中USB-Serial/JTAG（S3 原生外设）
ConfigManagerErrorCode0驱动正常，无设备错误
这一步避开的坑

本机同时存在 COM3 / COM4，但它们是 BTHENUM\…（蓝牙虚拟串口）。只看「有几个 COM 口」会误判。唯一可靠判据是 VID。

可复用结论

ESP32-S3 原生 USB 板不需要装任何 USB 转串口驱动。工具清单里列的 CH340 / CP210x，对这块板一个都用不上。

P1

最小闭环

先让「代码 → 编译 → 烧录 → 看到输出」这条路全程打通，此时完全不碰屏幕。屏幕是第二个变量，不能和第一个混在一起调。

一处必须改的配置

IDF 默认控制台是 UART0。这块板的 UART0 没有接到 USB 上，不改这一项，烧录会成功，但 COM5 一个字都不会有——这是最容易被误判成「烧录失败」的形态。

CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y

用双时钟互证

只用宿主时钟，「1 秒一行」可能只是巧合。让设备自己报时，两个互不相关的时钟都给出 1000 ms，才能排除观测误差。

时钟读数
设备自报 uptime（esp_timer）9007 → 10007 → 11007 … 严格 +1000
宿主侧 Stopwatch 打点1062 → 2062 → 3062 … 严格 +1000
本阶段产出

一个能跑的东西。按框架 §0.2，它从此成为不可协商的回归基线——后续任何改动都不得把它拆掉。

最关键的发现

屏幕的 RST 和背光压根不接 GPIO，而是走 XL9555 I/O 扩展芯片（I2C 地址 0x20）：SLCD_RST_IO = 0x0400、SLCD_PWR_IO = 0x0800。

这一条如果没查到，写出来的代码会编译通过、烧录成功、屏幕全黑——现象和「驱动写错」完全一样，会把排查引向错误方向。

P3

复用，而不是重写

决策：把厂商 components/BSP 整目录复制进工程，不自己写驱动。

复用的理由

  • 厂商 BSP 已在该硬件上验证过
  • 自写驱动要重调初始化序列、时序、扫描方向，产出不确定
  • 「能跑的东西不得在没有架构指令时重写」

代价（必须接受）

  • 代码不是你写的，出问题要读得懂
  • 与上游无同步机制——升级时会丢本地修改
  • 引入了厂商的旧版 I2C 驱动（已弃用）
P4

最小必要修改

厂商代码默认按 2.4 寸屏配置，本板是 1.3 寸。两处必改，都标了 /* ===== 本地修改（本项目） ===== */。

位置原值改为改错会怎样
lcd.c:29
SPI_LCD_TYPE		1（2.4寸）0（1.3寸）两套初始化序列完全不同 → 黑屏
lcd_display_dir()写死 320×240240×240窗口越界 + 清屏只刷一半，下半屏不更新
为什么第二处必须改

lcd_clear() 依赖 LCD_TOTAL_BUF_SIZE (320×240×2) 分块发送，而 240×240 只有它的一半。不改会导致下半屏残留旧内容。

P6

验证阶梯

「没报错」和「功能对」是两件事。证据要按强度分级，逐级往上爬——而且要说清楚当前证据支持到哪一级。

  1. ①编译 exit 0
  2. ②烧录 · Hash of data verified ×3
  3. ③启动日志 · 无 panic、无复位循环
  4. ④间接判据 · XL9555 未触发 esp_restart
  5. ⑤代码执行证据 · 打印出 panel: 240x240
  6. ⑥目视确认 · 屏幕上真的出现了文字

第 ④ 级的间接判据

xl9555_ioconfig() 失败时的代码是：重试 3 次仍失败则 esp_restart()。这意味着——

不需要看屏幕就能拿到的强证据

只要程序连续运行超过 15 秒没有重启，就说明 I2C 通信成功、XL9555 应答正常、屏幕复位与背光控制通路成立。

在无法目视的场景（远程设备、屏幕在背面、机箱内）下，这类判据尤其有价值。

第 ⑥ 级只有人能给

我看不到屏幕。在拿到用户那句「我看到屏幕上的内容了」之前，我能说的上限是「代码跑到了、通路成立了」——不是「显示成功了」。

P7

反馈迭代

用户反馈：配色太亮。

第一反应不该是调参数，而是先查「有没有得调」。把 BSP 全目录搜了一遍 ledc / PWM：零命中。

背光走 SLCD_PWR_IO（XL9555 的数字 IO），只有开和关两档，没有 PWM 通道。所以亮度无法软件调节，只能压低颜色值本身。

用途改前改后亮度
背景0x0000 纯黑0x1082 · RGB(16,16,16)—
标题0x07FF 满亮度青0x3AD1 · RGB(57,89,140)↓45%
正文0xFFFF 纯白0x94B2 · RGB(148,150,148)↓41%
强调0xF800 满亮度红0x9365 · RGB(148,109,41)↓42%

刺眼的元凶是纯白和满亮度红——这两个在 1.3 寸小屏上对比度过高。

可复用判断

遇到「太亮 / 太暗」这类反馈，先分清是可调参数问题（→ 调参数）还是通道能力问题（→ 只能换实现方式）。本板属于后者：真要调亮度得改硬件，把背光改接到带 LEDC 的 GPIO。

一个已实测确认无害的命名隐患

GPIO40 被两份代码定义为不同用途：lcd.h 说是 LCD_NUM_WR（DC），xl9555.h 说是 XL9555_INT_IO。启动日志显示先配为输入、后配为输出，最终生效的是 LCD 用途——实际硬件上 XL9555 的中断并未接到这个脚。不冲突，但属于厂商代码的命名隐患，记下来以免日后误解。

踩过的四个坑

其中两条是我自己的判断失误。照实写，因为这类错误的形态会重复出现。

坑表现根因教训
判 IDF 未安装 报「工具链不存在」 只查了 C:\esp 和系统环境变量，实际装在 D:\IDF-tools，且 IDF_PATH 只在 source profile 后才存在 查「不存在」必须先穷尽候选路径，否则「没找到」被误读成「没有」
给了未验证的命令 让用户跑 idf.py monitor，自己没先跑过 只验证了直接读串口，跳过了这条 给别人命令前，自己必须先跑通一次
错误归因 猜「没反应」是 DTR/RTS 把芯片拖进下载模式 没做对照实验就下结论 做了对照才推翻：DTR/RTS = 0/0 与 1/1 都有输出，S3 原生 USB 不理这两个信号
覆盖了出厂固件 第一次烧 hello world 时覆盖了 0x10000 的 factory 分区 没意识到出厂固件里可能藏着这条屏幕的引脚配置 烧录前先想：现有固件里有没有我需要的线索？这条线索一旦覆盖就没了
第三条的方法论

当「没反应」时，先找能区分的证据，再猜原因。这次的区分证据是：当时 COM5 能成功打开 ⇒ 说明没有任何终端在读它（idf.py monitor 会独占端口，实测占用时 Open 报 Access denied）⇒ 「没反应」是观测问题，不是固件问题。
